# Analytics Event Collection Service

Микросервис приёма пользовательских действий: кликов, просмотров страниц и кастомных событий. Сервис принимает события по HTTP, валидирует их, обогащает служебными полями и асинхронно публикует в Kafka для последующей аналитической обработки.

Документ описывает предметную область и проектируемую модель системы в соответствии с принципами Domain-Driven Design. Реализационные детали инфраструктуры не являются частью доменной модели и рассматриваются только там, где необходимы для определения границ приложения.

---

# 1. Возможности системы

Что умеет делать система: для каких целей к ней обращаются?

## События

- Принять событие клика (`click`).

- Принять событие просмотра страницы (`page_view`).

- Принять кастомное событие (`custom_event`).

Сервис не хранит события самостоятельно и не выполняет аналитических запросов: его обязанность — принять, проверить и доставить событие в очередь сообщений. Хранение, агрегация и аналитика находятся за пределами этого сервиса.

---

# 2. Правила предметной области

Правила предметной области определяют допустимое состояние системы и условия, при которых операции над ней являются корректными.

Правила не описывают HTTP, формат очереди, конкретные библиотеки, структуру сообщений или другие детали реализации.

## 2.1. Общие правила

### Идентификатор события

Каждое принятое событие обязано иметь уникальный идентификатор.

Идентификатор присваивается при приёме события, если он не был предоставлен клиентом.

### Принадлежность события

Событие принадлежит пользователю.

Пользователь идентифицируется значением `UserId`.

Анонимное действие представляется зарезервированным значением `UserId`, обозначающим отсутствие идентификации.

### Время события

Событие обязано иметь момент возникновения.

Если клиент не передал время события, сервис использует собственное текущее время.

### Тип события

Событие обязано иметь тип из фиксированного набора:

```text
CLICK
PAGE_VIEW
CUSTOM
```

Событие с типом вне набора отклоняется.

### Доставка ровно один раз

Каждое принятое событие должно быть опубликовано в очередь сообщений ровно один раз.

Повторный приём события с тем же идентификатором не должен приводить к дублированию в очереди.

Правило является доменной политикой (см. раздел 6) и обеспечивается механизмом очереди, а не проверкой внутри отдельного события.

---

## 2.2. Событие клика (click)

Событие клика описывает нажатие пользователем на элемент страницы.

При приёме события клика:

- `user_id` обязателен;

- `event_time` обязателен;

- `page_url` обязателен;

- `element_id` обязателен.

---

## 2.3. Событие просмотра страницы (page_view)

Событие просмотра описывает открытие пользователем страницы.

При приёме события просмотра:

- `user_id` обязателен;

- `event_time` обязателен;

- `page_url` обязателен;

- `duration` опционален и, если передан, должен быть неотрицательным.

---

## 2.4. Кастомное событие (custom_event)

Кастомное событие описывает произвольное действие, определяемое клиентом.

При приёме кастомного события:

- `user_id` обязателен;

- `event_time` обязателен;

- `event_name` обязателен;

- `payload` опционален.

---

# 3. Сущности предметной области

## 3.1. Событие (Event)

### Идентичность

`EventId` — уникальный идентификатор события.

### Назначение

`Event` представляет одно зафиксированное пользовательское действие и является корнем `Event Aggregate`.

### Состояние

- `EventId`

- `UserId`

- `EventType`

- `EventTime`

- `Payload`

### Инварианты

- `EventId` существует и уникален.

- `UserId` задан.

- `EventType` имеет допустимое значение.

- `EventTime` задан.

- `Payload` содержит только данные, допустимые для соответствующего типа события.

### Поведение

- `isType(type)`

Агрегат не публикует событие в очередь самостоятельно и не проверяет уникальность `EventId` во всей системе, поскольку это свойство множества событий, а не внутренний инвариант одного экземпляра `Event`.

---

# 4. Value Objects

Value Object определяется значением, а не идентичностью.

Value Object не имеет собственной жизненной идентичности и должен быть неизменяемым.

## 4.1. EventId

Представляет уникальный идентификатор события.

Инварианты:

- значение не пустое.

Поведение:

- сравнение значений.

Уникальность `EventId` не относится к `EventId` и проверяется за пределами Value Object.

---

## 4.2. UserId

Представляет идентификатор пользователя, которому принадлежит событие.

Инварианты:

- значение не пустое.

Анонимный пользователь представляется зарезервированным значением, определённым моделью предметной области.

---

## 4.3. EventType

Представляет тип события.

Допустимые значения:

```text
CLICK
PAGE_VIEW
CUSTOM
```

Инварианты:

- значение принадлежит допустимому набору.

Переходы между типами не определены: тип задаётся при создании события и не изменяется.

---

## 4.4. EventTime

Представляет момент возникновения события.

Инварианты:

- значение задано;

- значение находится в допустимых пределах (не ранее разумного прошлого и не позднее допустимого будущего).

Поведение:

- сравнение значений.

---

## 4.5. Payload

Представляет данные, специфичные для типа события.

Состав `Payload` зависит от `EventType`:

- для `CLICK`: `page_url`, `element_id`;

- для `PAGE_VIEW`: `page_url`, опционально `duration`;

- для `CUSTOM`: `event_name`, опционально произвольные данные.

Инварианты:

- коллекция существует;

- состав соответствует типу события.

Поведение:

- `asJson()` — сериализация для передачи в очередь.

---

## 4.6. PageUrl

Представляет адрес страницы, на которой произошло событие.

Инварианты:

- значение не пустое;

- значение соответствует формату URL.

---

## 4.7. ElementId

Представляет идентификатор элемента страницы, на котором произошёл клик.

Инварианты:

- значение не пустое.

---

## 4.8. EventName

Представляет имя кастомного события.

Инварианты:

- значение не пустое;

- длина находится в допустимых пределах.

---

# 5. Агрегаты

Агрегат является границей согласованности.

Каждый агрегат защищает собственные инварианты.

## 5.1. Event Aggregate

**Aggregate Root:** `Event`

```text
Event Aggregate
└── Event
    ├── EventId
    ├── UserId
    ├── EventType
    ├── EventTime
    └── Payload
```

## Ответственность

`Event` отвечает за корректность собственного состояния и поддержание собственных инвариантов.

## Инварианты

- идентификатор задан;

- пользователь задан;

- тип допустим;

- время задано;

- payload соответствует типу события.

## Поведение

```text
isType(type)
```

`Event` не отвечает за:

- отправку себя в очередь сообщений;

- уникальность собственного идентификатора среди всех событий;

- хранение или агрегацию событий.

Эти операции требуют контекста за пределами агрегата.

---

# 6. Доменные политики и правила между агрегатами

Не каждое бизнес-правило принадлежит агрегату.

Если правило требует знания нескольких агрегатов или состояния системы в целом, оно реализуется за пределами одного агрегата.

## 6.1. Доставка события ровно один раз

Для доставки события необходимо обеспечить:

```text
Event с указанным EventId публикуется в очередь ровно один раз.
```

Это правило относится к совокупности событий, а не к одному экземпляру `Event`.

Сценарий приёма события:

1. `EventApplicationService` присваивает `EventId`, если он не был предоставлен.

2. Событие публикуется в очередь с `EventId` в качестве ключа сообщения.

3. Продюсер очереди работает в идемпотентном режиме, защищающем от дублирования при повторных попытках доставки.

Предварительное назначение `EventId` не защищает от повторного приёма одного и того же события клиентом: окончательное устранение дублей выполняется потребителем на основе ключа события.

---

# 7. Application Layer

Application Layer реализует сценарии использования системы.

Application Service:

- принимает команду;

- получает необходимые данные;

- создаёт агрегат;

- вызывает его поведение;

- взаимодействует с портами;

- возвращает результат сценария.

Application Service не содержит бизнес-правила, которые принадлежат агрегатам.

---

## 7.1. EventApplicationService

## CollectEvent

1. Получить входные данные события.

2. Создать `EventId` (из входных данных или сгенерировать).

3. Создать `UserId` и `EventTime` (из входных данных или из `Clock`).

4. Создать `EventType` и `Payload` в соответствии с типом.

5. Создать `Event`.

6. Опубликовать событие через порт `EventProducer`, передав `EventId` как ключ сообщения.

7. Вернуть результат приёма (подтверждение доставки или ошибку).

Публикация события не является транзакционной операцией с хранилищем: сервис не ведёт собственного состояния, а результат операции определяется фактом успешной отправки в очередь.

---

# 8. Query Layer

Query Layer отсутствует.

Сервис не предоставляет операций чтения: события принимаются, проверяются и передаются в очередь, но не хранятся и не читаются самим сервисом.

---

# 9. Репозитории

Репозитории отсутствуют.

Сервис не загружает и не сохраняет агрегаты в собственном хранилище данных: срок жизни `Event` ограничен рамками одного сценария приёма события.

---

# 10. Доменные и прикладные порты

Порты определяют зависимости приложения от внешнего мира.

Порт принадлежит той части системы, которая формулирует требование к внешней зависимости.

Конкретная реализация порта находится во внешнем слое.

## EventProducer

Необходим для публикации события в очередь сообщений.

```text
publish(event, key) → Result
```

Конкретная технология очереди (Kafka) и формат сообщения не являются частью доменной модели.

## Clock

Предоставляет текущее время приложению.

```text
now() → DateTime
```

Использование абстракции времени позволяет не связывать доменную логику с системными часами и присваивать событию время приёма, когда клиент его не передал.

---

# 11. Границы слоёв

Архитектура системы:

```text
┌──────────────────────────────────────────────┐
│                 Presentation                 │
│ HTTP / CLI / другие интерфейсы              │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│                Application                   │
│ Application Services / Commands             │
│ Ports                                        │
└───────────────┬───────────────────┬──────────┘
                │                   │
                ▼                   ▼
┌────────────────────────┐   ┌─────────────────┐
│        Domain          │   │   Query Layer   │
│                        │   │                 │
│ Entities               │   │ (отсутствует)   │
│ Aggregates             │   │                 │
│ Value Objects          │   │                 │
│ Domain Rules           │   │                 │
└────────────────────────┘   └─────────────────┘
                ▲
                │
┌───────────────┴──────────────────────────────┐
│             Infrastructure                   │
│                                              │
│ Kafka producer adapter                       │
│ Settings                                     │
│ Clock implementation                         │
│ HTTP                                        │
└──────────────────────────────────────────────┘
```

Зависимости направлены внутрь.

Доменная модель не должна зависеть от:

- FastAPI;

- Kafka;

- конкретного формата сериализации;

- HTTP;

- конкретного транспорта.

---

# 12. Domain Layer

Доменный слой содержит только модель предметной области.

```text
domain/
└── event/
    ├── event.py
    ├── event_id.py
    ├── user_id.py
    ├── event_type.py
    ├── event_time.py
    ├── payload.py
    ├── page_url.py
    ├── element_id.py
    ├── event_name.py
    └── exceptions.py
```

Доменный слой не знает о Application Services.

---

# 13. Application Layer

Application Layer содержит сценарии использования.

```text
application/
├── events/
│   ├── services.py
│   └── dto/
│
└── ports/
    ├── event_producer.py
    └── clock.py
```

---

# 14. Infrastructure Layer

Infrastructure Layer содержит реализации портов.

```text
infrastructure/
├── kafka/
│   └── event_producer.py
│
├── clock/
│
├── settings.py
│
├── health.py
│
└── container.py
```

Infrastructure Layer может зависеть от Application и Domain Layer, но Domain Layer не зависит от Infrastructure.

---

# 15. Presentation Layer

Presentation Layer предоставляет внешние интерфейсы системы.

```text
presentation/
└── api/
    ├── application.py
    ├── schemas.py
    ├── errors.py
    └── routers/
        ├── events.py
        └── health.py
```

HTTP-контроллеры не содержат предметной логики.

Они преобразуют внешние данные в команды Application Layer и преобразуют результаты Application Layer в соответствующий формат ответа.

---

# 16. Внешние зависимости

Внешние системы подключаются через порты Application Layer.

```text
Application
    │
    └── EventProducerPort
            └── aiokafka implementation (enable_idempotence=True)
```

Конкретная реализация очереди (Kafka через aiokafka) не является частью доменной модели.

---

# 17. Итоговая модель

Система состоит из одного агрегата:

```text
Event Aggregate
    ├── EventId
    ├── UserId
    ├── EventType
    ├── EventTime
    └── Payload
```

Агрегат не содержит ссылок на другие агрегаты.

`Event` является самодостаточным значением, описывающим одно пользовательское действие.

---

# 18. Основной бизнес-сценарий

## Приём события

```text
Request
  ↓
EventApplicationService
  ↓
создание EventId (при необходимости)
  ↓
создание EventType + Payload
  ↓
создание Event
  ↓
EventProducer.publish(event, key=EventId)
  ↓
ack (подтверждение доставки)
```

---

# 19. Принципы проектирования

При реализации системы соблюдаются следующие принципы:

1. Агрегат является границей согласованности.

2. Aggregate Root является единственной точкой изменения внутреннего состояния агрегата.

3. Value Objects не имеют собственной идентичности.

4. Инварианты одного агрегата защищаются самим агрегатом.

5. Правила, требующие нескольких агрегатов, координируются Application Layer или специализированной Domain Policy.

6. Application Service реализует сценарий использования, а не доменную сущность.

7. Внешние зависимости подключаются через порты.

8. Domain Layer не зависит от Infrastructure Layer.

9. Конкретные технологии не должны определять модель предметной области.

10. Доменная модель не должна содержать HTTP, Kafka, формат сериализации и другие технические детали.

11. Реализация начинается после завершения определения предметной модели, агрегатов, инвариантов и сценариев использования.

12. Код должен следовать сформированной модели, а не изменять её неявно в процессе реализации.
