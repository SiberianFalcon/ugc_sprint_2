# Analytics Event Transfer Service (ETL)

Микросервис непрерывного переноса пользовательских действий из Kafka в аналитическое хранилище ClickHouse. Сервис читает события, опубликованные API-сервисом приёма, нормализует их под схему хранилища и записывает в ClickHouse, обеспечивая устойчивость к сбоям источника и хранилища.

Документ описывает предметную область и проектируемую модель системы в соответствии с принципами Domain-Driven Design. Реализационные детали инфраструктуры не являются частью доменной модели и рассматриваются только там, где необходимы для определения границ приложения.

---

# 1. Возможности системы

Что умеет делать система: для каких целей к ней обращаются?

## Перенос событий

- Непрерывно читать события из очереди сообщений.

- Нормализовать события под схему аналитического хранилища.

- Записывать события в аналитическое хранилище пакетами.

- Фиксировать прогресс чтения очереди.

Сервис работает в фоновом режиме и не предоставляет HTTP-интерфейса. Он переносит события трёх типов: `click`, `page_view` и `custom_event`.

---

# 2. Правила предметной области

Правила предметной области определяют допустимое состояние системы и условия, при которых операции над ней являются корректными.

Правила не описывают HTTP, конкретные библиотеки, структуру таблиц, формат сериализации или другие детали реализации.

## 2.1. Общие правила

### Источник событий

Источником событий является очередь сообщений, в которую события публикует сервис приёма.

Событие в очереди имеет уникальный ключ, соответствующий идентификатору события.

### Порядок обработки

События обрабатываются в порядке их появления в очереди в рамках одной партиции.

Сервис не гарантирует глобальный порядок между разными партициями.

### Прогресс обработки

Сервис обязан фиксировать прогресс чтения очереди.

После фиксации прогресса событие считается обработанным и не читается повторно при штатной работе.

### Доставка не реже одного раза

Каждое прочитанное событие должно быть записано в хранилище не реже одного раза.

При сбое между чтением и фиксацией прогресса допускается повторная запись одного и того же события.

### Устранение дублей

Повторная запись одного и того же события не должна приводить к искажению итоговых аналитических данных.

Устранение дублей выполняется на стороне хранилища по идентификатору события.

### Устойчивость к сбоям

Сервис должен продолжать работу при временной недоступности очереди сообщений.

Сервис должен продолжать работу при временной недоступности аналитического хранилища.

При невозможности записать событие сервис повторяет попытку с ограниченной частотой, не теряя события.

---

## 2.2. Нормализация события

При переносе события:

- идентификатор события сохраняется и используется как ключ устранения дублей;

- идентификатор пользователя сохраняется;

- тип события сохраняется;

- время события сохраняется;

- данные события (`payload`) преобразуются в плоское представление, пригодное для хранения и агрегации.

Событие с недопустимым или отсутствующим обязательным полем не должно записываться в хранилище: оно фиксируется отдельно как непригодное к обработке.

---

## 2.3. Граница пакета

Запись событий в хранилище выполняется пакетами, а не по одному.

Пакет формируется по количеству событий или по времени ожидания, в зависимости от того, какое условие наступит раньше.

Фиксация прогресса чтения выполняется только после успешной записи всего пакета.

---

# 3. Сущности предметной области

## 3.1. Событие (Event)

### Идентичность

`EventId` — уникальный идентификатор события.

### Назначение

`Event` представляет одно пользовательское действие, прочитанное из очереди и подготовленное к записи в хранилище.

### Состояние

- `EventId`

- `UserId`

- `EventType`

- `EventTime`

- `Payload`

### Инварианты

- `EventId` существует и уникален.

- `UserId` задан.

- `EventType` имеет допустимое значение.

- `EventTime` задан.

- `Payload` содержит данные, допустимые для соответствующего типа события.

### Поведение

- `normalize()` — преобразование в представление, пригодное для хранения.

- `isType(type)`

Схема `Event` совпадает со схемой, по которой API-сервис публикует события в очередь. Это общий контракт между двумя сервисами; `Event` как значение не принадлежит ни одному из них.

---

# 4. Value Objects

Value Object определяется значением, а не идентичностью.

Value Object не имеет собственной жизненной идентичности и должен быть неизменяемым.

## 4.1. EventId

Представляет уникальный идентификатор события.

Инварианты:

- значение не пустое.

`EventId` является ключом устранения дублей в хранилище.

---

## 4.2. UserId

Представляет идентификатор пользователя, которому принадлежит событие.

Инварианты:

- значение не пустое.

---

## 4.3. EventType

Представляет тип события.

Допустимые значения:

```text
CLICK
PAGE_VIEW
CUSTOM
```

Инварианты:

- значение принадлежит допустимому набору.

---

## 4.4. EventTime

Представляет момент возникновения события.

Инварианты:

- значение задано.

---

## 4.5. Payload

Представляет данные, специфичные для типа события.

Состав `Payload` зависит от `EventType`:

- для `CLICK`: `page_url`, `element_id`;

- для `PAGE_VIEW`: `page_url`, опционально `duration`;

- для `CUSTOM`: `event_name`, опционально произвольные данные.

Инварианты:

- коллекция существует;

- состав соответствует типу события.

Поведение:

- `asRecord()` — представление для записи в хранилище.

---

# 5. Агрегаты

Агрегат является границей согласованности.

Каждый агрегат защищает собственные инварианты.

## 5.1. Event Aggregate

**Aggregate Root:** `Event`

```text
Event Aggregate
└── Event
    ├── EventId
    ├── UserId
    ├── EventType
    ├── EventTime
    └── Payload
```

## Ответственность

`Event` отвечает за корректность собственного состояния и преобразование в представление хранилища.

## Инварианты

- идентификатор задан;

- пользователь задан;

- тип допустим;

- время задано;

- payload соответствует типу события.

## Поведение

```text
normalize()
isType(type)
```

`Event` не отвечает за:

- чтение из очереди сообщений;

- запись в хранилище;

- фиксацию прогресса обработки.

Эти операции требуют контекста за пределами агрегата.

---

# 6. Доменные политики и правила между агрегатами

Не каждое бизнес-правило принадлежит агрегату.

Если правило требует знания нескольких агрегатов или состояния системы в целом, оно реализуется за пределами одного агрегата.

## 6.1. Доставка не реже одного раза и устранение дублей

Для переноса события необходимо обеспечить:

```text
Event записан в хранилище не реже одного раза.
```

При сбое между записью события и фиксацией прогресса чтения одно и то же событие может быть записано повторно.

Окончательное устранение дублей обеспечивается хранилищем:

```text
хранилище устраняет дубли по EventId.
```

Механизм устранения дублей является обязанностью хранилища, а не отдельного экземпляра `Event`.

---

## 6.2. Фиксация прогресса

Прогресс чтения фиксируется только после успешной записи всего пакета:

```text
прочитать пакет
        ↓
записать пакет в хранилище
        ↓
зафиксировать прогресс
```

Если запись пакета не удалась, прогресс не фиксируется, и пакет будет прочитан повторно.

---

## 6.3. Обработка непригодных событий

Событие, которое не может быть записано из-за недопустимого содержимого, не должно блокировать обработку остальных событий.

Такое событие фиксируется отдельно от основного хранилища, а обработка потока продолжается.

---

# 7. Application Layer

Application Layer реализует сценарии использования системы.

Application Service:

- принимает команду;

- получает необходимые данные;

- создаёт агрегат;

- вызывает его поведение;

- взаимодействует с портами;

- управляет границей пакета;

- возвращает результат сценария.

Application Service не содержит бизнес-правила, которые принадлежат агрегатам.

---

## 7.1. EventTransferService

## Run

Циклический сценарий непрерывного переноса:

1. Прочитать пакет событий из очереди через порт `EventConsumer`.

2. Для каждого события создать `Event` и вызвать `Event.normalize()`.

3. Записать пакет в хранилище через порт `EventRepository`.

4. Если запись пакета успешна, зафиксировать прогресс через порт `OffsetStore`.

5. Если запись не удалась из-за сбоя хранилища, повторить попытку с задержкой, не фиксируя прогресс.

6. События, непригодные к обработке, передать через порт `DeadLetterStore` и продолжить обработку.

7. Повторять сценарий непрерывно.

Пакетная запись и фиксация прогресса координируются Application Service, а не отдельным агрегатом.

---

# 8. Query Layer

Query Layer отсутствует.

Сервис не предоставляет операций чтения данных: он только переносит события из очереди в хранилище.

---

# 9. Репозитории

Репозиторий представляет коллекцию агрегатов с точки зрения доменной модели.

Репозитории используются для загрузки и сохранения агрегатов.

## EventRepository

```text
saveBatch(events) → Result
```

`EventRepository` отвечает за запись пакета нормализованных событий в аналитическое хранилище и устранение дублей по `EventId`.

Конкретный механизм устранения дублей (например, `ReplacingMergeTree`) является деталью реализации и не относится к доменной модели.

---

# 10. Доменные и прикладные порты

Порты определяют зависимости приложения от внешнего мира.

Порт принадлежит той части системы, которая формулирует требование к внешней зависимости.

Конкретная реализация порта находится во внешнем слое.

## EventConsumer

Необходим для чтения пакета событий из очереди сообщений.

```text
pollBatch(maxSize, timeout) → Batch
```

Конкретная технология очереди (Kafka) и формат сообщения не являются частью доменной модели.

## EventRepository

Необходим для записи пакета событий в аналитическое хранилище.

```text
saveBatch(events) → Result
```

## OffsetStore

Необходим для фиксации прогресса чтения очереди.

```text
commit(offset) → Result
```

## DeadLetterStore

Необходим для фиксации событий, непригодных к обработке.

```text
save(event) → Result
```

## Clock

Предоставляет текущее время приложению.

```text
now() → DateTime
```

Используется для формирования границы пакета по времени ожидания.

# 15. Presentation Layer

Presentation Layer отсутствует.

Сервис работает в фоновом режиме и не предоставляет внешнего интерфейса. Мониторинг состояния процесса осуществляется через метрики и логи, а не через HTTP-эндпоинты.

---

# 16. Внешние зависимости

Внешние системы подключаются через порты Application Layer.

```text
Application
    │
    ├── EventConsumerPort
    │       └── aiokafka consumer implementation
    │
    ├── EventRepositoryPort
    │       └── ClickHouse implementation
    │
    ├── OffsetStorePort
    │       └── Kafka offset commit implementation
    │
    └── DeadLetterStorePort
            └── отдельная очередь/хранилище непригодных событий
```

Конкретные технологии (Kafka через aiokafka, ClickHouse через clickhouse-connect) не являются частью доменной модели.

---

# 17. Итоговая модель

Система состоит из одного агрегата:

```text
Event Aggregate
    ├── EventId
    ├── UserId
    ├── EventType
    ├── EventTime
    └── Payload
```

Агрегат не содержит ссылок на другие агрегаты.

`Event` является общим контрактом между сервисом приёма и сервисом переноса: API публикует его в очередь, ETL читает и записывает в хранилище.

---

# 18. Основной бизнес-сценарий

## Непрерывный перенос

```text
EventConsumer.pollBatch()
        ↓
Event.normalize() для каждого события
        ↓
EventRepository.saveBatch()
        ├── успех → OffsetStore.commit()
        └── сбой хранилища → повтор с задержкой
                            (без фиксации прогресса)
        ↓
повторить
```

Непригодное событие передаётся в `DeadLetterStore`, не прерывая поток.

---

# 19. Принципы проектирования

При реализации системы соблюдаются следующие принципы:

1. Агрегат является границей согласованности.

2. Aggregate Root является единственной точкой изменения внутреннего состояния агрегата.

3. Value Objects не имеют собственной идентичности.

4. Инварианты одного агрегата защищаются самим агрегатом.

5. Правила, требующие нескольких агрегатов, координируются Application Layer или специализированной Domain Policy.

6. Application Service реализует сценарий использования, а не доменную сущность.

7. Репозитории используются для записи агрегатов.

8. Внешние зависимости подключаются через порты.

9. Domain Layer не зависит от Infrastructure Layer.

10. Конкретные технологии не должны определять модель предметной области.

11. Доменная модель не должна содержать Kafka, ClickHouse, формат сериализации и другие технические детали.

12. Устранение дублей и устойчивость к сбоям обеспечиваются на уровне хранилища и координации, а не внутри отдельного агрегата.

13. Реализация начинается после завершения определения предметной модели, агрегатов, инвариантов и сценариев использования.

14. Код должен следовать сформированной модели, а не изменять её неявно в процессе реализации.
