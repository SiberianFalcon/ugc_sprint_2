# ADR-0001: Выбор хранилища пользовательского контента

- **Статус:** принято
- **Дата:** 2026-10-02
- **Контекст:** API контента (лайки, закладки, рецензии)

## Контекст

Требуется хранилище для пользовательского контента — лайков, закладок и
рецензий — с жёстким требованием к скорости чтения (< 200 мс). Нагрузка:
~3 млн MAU, данные распределены по пользователям и фильмам.

## Рассматриваемые варианты

- **MongoDB** — документное хранилище, гибкая схема рецензий, уникальные
  индексы для идемпотентности действий.
- **PostgreSQL** — реляционная БД с ACID-гарантиями и зрелой экосистемой.

## Решение

Выбрана **MongoDB**. Сравнение проводилось на датасете 10 млн записей
(`research/storage/`): одинаковый набор данных и индексов загружался в обе БД,
замерялись p50/p95/p99 точечного чтения, подсчёта, постраничного списка,
upsert и удаления. Обе базы уложились в требование < 200 мс (p95 чтений
< 2 мс), при этом на подсчёте лайков фильма MongoDB стабильнее
(p95 0.8 мс против 21.3 мс у PostgreSQL).

Ключевые факторы:

- гибкая схема рецензий без миграций;
- встроенная поддержка идемпотентных upsert с уникальным индексом;
- достаточная производительность чтений под требование < 200 мс;
- стабильные задержки на агрегатных подсчётах;
- совместимость с асинхронным Python-стеком (`motor`).

## Последствия

- Добавлена зависимость `motor`/`pymongo`.
- Индексы: уникальный `(user_id, film_id)` для лайков/закладок,
  `(film_id, kind, created_at DESC)` и `(user_id, created_at DESC)` для
  рецензий.
- Итоговая таблица результатов — в `README.md` и
  `research/storage/README.md`.
